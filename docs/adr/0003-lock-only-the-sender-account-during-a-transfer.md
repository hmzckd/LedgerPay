# Lock only the sender account during a transfer

Two transfers from the same account must never both pass the balance check, or the account could go below zero. Each transfer runs in one database transaction that first locks the sender's row in `accounts` with `SELECT ... FOR NO KEY UPDATE` and only then sums the balance, so a second transfer from the same account waits until the first one commits or rolls back and then sees the new balance. Read committed is enough for this, because the balance query starts after the lock is granted and so sees every transfer committed before it. Only the sender is locked: money coming in can never push an account below zero, so receivers and deposits never wait. We use `FOR NO KEY UPDATE` instead of `FOR UPDATE` because inserting a transfer and its ledger entries checks their foreign keys with a `FOR KEY SHARE` lock on each account row, and `FOR UPDATE` blocks that lock: with `FOR UPDATE`, two opposite transfers (A to B and B to A) each held one account and waited for the other, and PostgreSQL ended one of them with a deadlock error. We rejected the serializable isolation level, which would also stop the double spend but fails conflicting transactions with serialization errors that every caller would have to retry, while a row lock simply makes them wait their turn.
